장애 보고서

INCIDENT · SEV-1

자동 업데이트 한 번에 전 서비스 26시간 19분 중단

영향: 가상 키 API · RAG DB · Gitea · Prometheus · 데이터 손실 0

원인 추적

  1. load average 약 9,100인데 CPU 사용률은 2%. 프로세스가 I/O 대기(D state)에 묶였다고 판단
  2. 영향받은 서비스의 공통점은 모두 nfs-csi PVC. node_nfsd_packets_total이 멈춰 있음
  3. journalctl: rpc.nfsd가 errno 12로 기동 실패
  4. 재시작 주체는 사람이 아니라 unattended-upgrades + needrestart. 58일 무재부팅으로 커널 메모리 단편화
  5. 알림이 없던 이유: Prometheus도 같은 NFS 위에 있었고, Alertmanager receiver가 null

재발 방지

  • 자동 업데이트 비활성화, 패치는 점검 시간에 수동 적용 ADR-043
  • 새 커널에 RAID 드라이버가 없어 재부팅 시 부팅 불가 상태임을 발견. 커널 고정 + 드라이버 재빌드 절차 문서화 ADR-044
  • 단일 NFS·알림 부재는 Tier별 RTO/RPO와 8주 멀티노드 전환 계획에 편입 ADR-045

감시 체계는 감시 대상과 분리되어야 한다.

CMYK Grayspot Detection System

기간
2026.03 – 2026.06
역할
R2 Model & Training · SA
팀

C/M/Y/K 채널별 이미지에서 결함 수준을 분류합니다. 비지도 사전학습과 지도 분류학습을 결합한 2단계 학습 구조, Swing Architecture를 설계했습니다.

  • SSOT 모든 파라미터·경로를 config 단일 원천으로. 하드코딩 경로 제거, Fail-Fast 검증 코드(SSOT-FF01 등) 설계

OT냐 CRDT냐

OT는 서버가 모든 충돌을 중재해야 합니다. MSA 분산 구조에서 100명 동시 편집이라는 목표라면 부하가 한곳에 몰린다고 판단해, 클라이언트가 독립적으로 연산하고 나중에 병합하는 CRDT(Y.js)를 골랐습니다.

P2P냐 SFU냐

P2P는 참가자가 늘면 연결 수가 제곱으로 늘어납니다. 확장성 한계를 분석한 뒤 MediaSoup SFU로 설계를 전환했고, 50명 동시 접속 음성 통화를 안정적으로 통과했습니다.

팀이 기다리지 않게

S-04

일하는 원칙

구조가 품질을 결정한다

SSOT, HLD/LLD, Contract처럼 팀 전체가 같은 기준으로 움직이는 구조를 먼저 만들면, 개인 기술의 차이보다 더 큰 품질 차이가 납니다.

장애는 대부분 변경에서 시작된다

가장 큰 장애는 공격도 고장도 아닌 자동 업데이트에서 왔습니다. 그래서 코드로 관리되는 인프라와 Git 기반 배포를 어떤 기술보다 먼저 둡니다.

드러나지 않는 문제를 찾는다

인수인계 문서를 쓰며 전 항목을 kubectl·helm으로 실사 검증하다가, 알림이 누구에게도 가지 않는 상태를 발견했습니다. 증상이 아니라 구조적 원인을 봅니다.

담당자만 아는 환경을 만들지 않는다

설계한 사람이 없어도 돌아가야 합니다. 권한을 팀 단위로 나누고, 실제 장애 사례를 기준으로 가이드라인과 학습 로드맵을 남겼습니다.
